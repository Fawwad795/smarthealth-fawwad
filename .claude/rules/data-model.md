# Data model rules

Appendix B of the guidelines is a **starting point**, not a specification —
differences are fine, but each one must be justified in `docs/design.md`.

## Tables

`users`(email unique, password_hash, role enum patient/provider/front_desk/admin) ·
`patients`(user_id, dob, contact JSONB) · `providers`(user_id, specialty, department_id, bio) ·
`departments`(name, clinic, order_index) ·
`services`(department_id, name, description, prep_instructions, status, published_at) ·
`slots`(provider_id, start_time, end_time, status AVAILABLE/RESERVED/BOOKED/BLOCKED) ·
`appointments`(patient_id, provider_id, slot_id, service_id, status, idempotency_key, booked_at) ·
`appointment_status_history`(from_status, to_status, actor, reason) ·
`slot_reservations`(appointment_id, slot_id, status RESERVED/RELEASED/COMMITTED) — makes reserve idempotent + compensable ·
`billing`(appointment_id, amount, status PENDING/CHECKED/FAILED/REFUNDED, idempotency_key) ·
`visits`(appointment_id, checked_in_at, completed_at, status) ·
`waitlist`(provider_id, patient_id, status) ·
`content_chunks`(source_type, source_id, chunk_index, text, token_count, text_hash, embedded_at) ·
`chunk_embeddings`(chunk_id, embedding vector, model) ·
`outbox_events`(event_id, event_type, payload JSONB, correlation_id, published_at) ·
`processed_events`(event_id unique, consumer, processed_at) ·
`failed_jobs`(job_type, payload JSONB, error, attempts) — the dead-letter table ·
`notifications`(user_id, type, payload JSONB, status) ·
`idempotency_keys`(key, user_id, endpoint, response JSONB) — or Redis with TTL ·
`analytics_daily`(date, appointments_booked, completed_visits, cancellations, avg_wait_seconds, …) ·
`ai_interactions`(user_id, intent, retrieved_ids JSONB, answer, model, prompt_version, input_tokens, output_tokens, latency_ms, refused) ·
`generated_content`(appointment_id/report_scope, type, content JSONB, model, prompt_version).

## Conventions established in Week 1 — follow them

- **Every table gets `created_at` / `updated_at`, UTC and timezone-aware**, via
  `TimestampMixin`. They are `server_default=func.now()` so Postgres owns the clock:
  by Week 3 four processes write rows and ordering them needs one clock.
- **`onupdate` is a SQLAlchemy-side mechanic, not a database default.** An ORM update
  moves `updated_at`; a raw `UPDATE` does not. **The Week 2 slot reservation is raw
  SQL, so it must set `updated_at = now()` itself.**
- **Enums are `VARCHAR` + `CHECK`, never native Postgres `ENUM`**, always built via
  `enum_column()` in `app/models/enums.py`. Postgres has no `DROP VALUE`, so
  downgrading a native enum means recreating the type and re-casting the column.
  `create_constraint=True` is **not** the SQLAlchemy default — without it the column
  enforces nothing.
- **`StrEnum` with names equal to values.** These strings land in rows and event
  payloads; an f-string must render `AVAILABLE`, not `SlotStatus.AVAILABLE`.
- **Status enums, never boolean flags.** A boolean cannot express "a workflow is
  running right now" or "the last attempt failed".
- **Availability is discrete `Slot` rows, never a boolean on the provider.** A boolean
  has no identity, so no appointment could reference it and two writers would have
  nothing to conflict over.
- **A naming convention on `Base.metadata`** so every constraint name is derivable
  from a rule rather than discovered by inspecting one particular database.
- **Every FK is `ON DELETE RESTRICT`.** Rows are deactivated or transitioned, never
  deleted.
- **Index anything filtered or joined on** — but not a column already covered as the
  leading column of a composite index, which is pure write cost.
- **`slots` carries an `EXCLUDE` constraint** (`ex_slots_no_overlap`, needs
  `btree_gist`) preventing two overlapping slots for one provider. The unique
  `(provider_id, start_time)` is kept alongside it for its B-tree index and clearer
  errors. `CHECK (end_time > start_time)` is not cosmetic: an empty range overlaps
  nothing in Postgres, so a zero-length slot would slip past the exclusion constraint.

## Migrations

- **Alembic only — no `create_all()` in application code, ever.**
  `alembic upgrade head` must build the whole schema from an empty DB.
- Every model change gets a revision, in the same commit as the model.
- **Every new model must be added to `app/models/__init__.py`.** A model nothing
  imports is invisible to SQLAlchemy and to Alembic — and if its table already
  exists, autogenerate reads the diff as "removed table" and emits `op.drop_table()`.
- Always read an autogenerated migration before applying it, and always write a
  working `downgrade()`. Round-trip it.
- pgvector is enabled by a migration (`CREATE EXTENSION IF NOT EXISTS vector`), never
  by hand.
